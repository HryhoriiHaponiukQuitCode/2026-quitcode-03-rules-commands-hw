# Lead Sync — архітектурна записка

> Джерело істини для правил проєкту (Task A). Записку писали для людей: тут є і
> «чому», і історія. Ваше завдання — перетворити її на **короткі правила, які
> виконує агент**. Проєкт і дані синтетичні (домени `*.example.test`).

## Що це за сервіс

`lead-sync` — воркер, який агенція перенесла з n8n-воркфлоу для клієнта Studio Nova.
Кожні 5 хвилин він бере нові заявки з форми сайту й розсилає їх в інтеграції:
Slack-канал менеджерів, Google-таблицю, а далі — CRM і месенджери. Раніше це був
воркфлоу з восьми нод; тепер це TypeScript, Node 22+ і тести на Vitest.

## Шари і напрям залежностей

```
app/src/
  core/          платформа: типи, HTTP, конфіг, парсинг, логер
  integrations/  по одному модулю на зовнішню систему + реєстр index.ts
  sync/          запуск синхронізації і стан між запусками
```

- `integrations/` і `sync/` імпортують з `core/`. `core/` не імпортує нічого з решти проєкту.
- `integrations/` нічого не знають про `sync/`. `sync/` працює з інтеграціями лише
  через контракт `Integration` з `core/types.ts` і реєстр `integrations/index.ts`.
- Нова зовнішня система — це новий файл `src/integrations/<kebab-name>.ts`, тест
  поруч (`<kebab-name>.test.ts`) і один рядок у `integrations/index.ts`. Більше нічого.

## Ядро (`src/core/`) — захищена зона

`core/` належить платформній команді: той самий core працює в усіх клієнтських
воркерах агенції. Зміни в ньому йдуть окремим PR через рев'ю цієї команди, тому
**у звичайних задачах `src/core/**` не редагується взагалі** — ні «дрібний фікс»,
ні «додам один тип». Якщо задача без цього не робиться, треба зупинитись і
описати, що саме потрібно змінити в core і навіщо.

Публічний API ядра — рівно ось це. Іншого не існує, і вигадувати його не можна:

| Модуль | Експорт | Для чого |
|---|---|---|
| `core/types.ts` | `Lead`, `Result<T>`, `Integration` | спільні типи й контракт інтеграції |
| `core/http.ts` | `postJson(url, body, options?)` → `Promise<Result<string>>`, `PostOptions` | будь-який вихідний HTTP: таймаут, повтори на 5xx/429 |
| `core/config.ts` | `readEnv(name)` → `Result<string>` | читання змінних середовища |
| `core/parse.ts` | `parseJson(text, guard, label?)` → `Result<T>`, `Guard<T>`, `isRecord`, `isString`, `isNumber` | перетворення зовнішнього тексту на дані |
| `core/log.ts` | `log.info`, `log.warn`, `log.error`, `redact(text)` | журнал із маскуванням секретів |

Так само не редагуються: `app/scripts/**` (перевірка правил), `materials/**`,
`.coderabbit.yaml`, `.github/**`.

## Конвенції коду

1. **Помилки — це значення.** Функції, що можуть не вдатися, повертають `Result<T>`.
   Інтеграція не кидає винятків назовні: `send()` завжди повертає `Result<void>`.
2. **HTTP — лише через `postJson()`.** Прямого `fetch` в інтеграціях немає: у ньому
   нема таймауту, повторів і маскування URL у журналі. Нових HTTP-клієнтів (axios,
   got, ky) не додаємо.
3. **Змінні середовища — лише через `readEnv()`.** `process.env` поза `core/config.ts`
   не читаємо. Значення секретів не пишемо в журнал і не вшиваємо в код, навіть
   «тимчасово».
4. **Зовнішнім даним не довіряємо.** Будь-який JSON — відповідь API, тіло вебхука,
   файл стану — розбирається лише через `parseJson(text, guard)` з guard на
   очікувану форму. Невалідний JSON або неочікувана форма — це помилка
   (`Result` з `ok: false`), яку видно в журналі. Тихо підставити «значення за
   замовчуванням» і працювати далі — не можна: так пошкоджені дані стають
   непомітними, а наслідки — дорогими.
5. **Журнал — лише через `log`.** `console.*` поза `core/log.ts` не використовуємо:
   `log` маскує токени, а `console.log` друкує їх як є.
6. **Без `any`.** Для невідомих даних — `unknown` плюс guard.
7. **Без нових залежностей.** У застосунку нуль runtime-залежностей, і так має
   лишитись. Потрібна бібліотека — спершу питання в PR, а не `npm install`.
8. **Мінімізація даних.** У сповіщення (Slack, месенджери) не передаємо email і
   телефон ліда — лише ім'я, джерело й бюджет. Повні дані йдуть тільки в системи
   обліку (таблиця, CRM).
9. **Імена.** Файли — kebab-case; поле `name` інтеграції збігається з іменем файлу.

## Тести

- Vitest, файл `*.test.ts` поруч із модулем. Реальної мережі в тестах немає:
  `fetch` підміняється через `vi.stubGlobal("fetch", ...)`, змінні — через `vi.stubEnv`.
- Для кожної інтеграції: успішна відправка (перевірити URL і тіло запиту),
  відсутня змінна середовища, помилка від зовнішньої системи.
- Перед комітом: `cd app && npm test && npm run typecheck && npm run check:rules`.

## Спадщина

Частину коду перенесли з n8n до появи цієї записки, і конвенціям він не
відповідає — `npm run check:rules` показує, де саме. Такий код переписують
поступово, окремою задачею і **без зміни поведінки**, яку фіксують тести
(URL, тіло запиту, тексти помилок).
