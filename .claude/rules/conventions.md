# Conventions — як пишемо код у lead-sync

## Контекст

Кожен пункт закриває реальний клас дефектів: секрети в логах, падіння на
неочікуваній відповіді, тихе пошкодження стану. Пояснення «чому» — у
`materials/architecture-brief.md`.

## Правило

- **Помилки — значення.** Функції, що можуть не вдатися, повертають `Result<T>`.
  `send()` інтеграції не кидає винятків — лише `Result<void>`.
- **HTTP** — тільки `postJson()` з `core/http.ts`. Не `fetch`, не axios / got / ky.
- **Змінні середовища** — тільки `readEnv("NAME")`. Не `process.env`. Значення
  секретів не логуй і не вшивай у код.
- **Будь-який JSON** — відповідь API, вебхук, файл стану — тільки
  `parseJson(text, guard, "label")`. Не `JSON.parse`. Невалідний JSON або
  неочікувана форма → `{ ok: false }` і запис у `log.error`. **Ніколи** не
  підставляй мовчки значення за замовчуванням.
- **Журнал** — тільки `log.info` / `log.warn` / `log.error`. Не `console.*`: він не маскує токени.
- **Типи** — без `any`: `unknown` плюс guard.
- **Залежності** — не додавай пакетів і не імпортуй нічого, крім відносних шляхів і
  `node:*`. Потрібна бібліотека — спитай людину.
- **Сповіщення** (Slack, месенджери) — лише ім'я, джерело й бюджет. Без email і телефону.
- **Тести** — поруч із модулем; `vi.stubGlobal("fetch", …)` і `vi.stubEnv(…)`, без
  реальної мережі. Для інтеграції мінімум: успіх (URL і тіло), відсутня змінна
  середовища, помилка зовнішньої системи.

## Як перевірити

- `cd app && npm test && npm run typecheck && npm run check:rules` — тести зелені,
  а `check:rules` не показує порушень у файлах, які ти змінив.
